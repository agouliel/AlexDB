We also need a MoreView with placeholders for Books/Tickets/Files noting "API required". Edit/create require authentication — login involves grabbing a CSRF cookie via GET, then POSTing credentials with the CSRF token and Referer header, following redirects, and checking whether a sessionid cookie appears or whether the final URL still points to the login/form page to detect failure. The default base URL will point to the Django server over HTTPS (keeping ATS happy).

We won't persist passwords, just rely on session cookies via HTTPCookieStorage. Setting up a generic decodable page struct for DataTables responses with filtered record counts and data, plus query parameters for draw, pagination, search, and sorting.

It's a SwiftUI app for iOS 17 and up, with the Xcode project generated from  project.yml ; Installed XcodeGen via Homebrew to do that.

What works with existing Django endpoints

• Songs, Artists, Albums: searchable lists that load more as you scroll, plus an artist detail screen showing its albums and songs.
• Login: the app logs in through the existing Django login form.
• Songs, when logged in: add, edit and delete use the existing HTML form endpoints. The app guesses success from where the server redirects, so it's fragile until a proper JSON API exists.
• Base URL: editable in the More tab.

What needs a new API on the Django side
Books, Tickets and Files only have HTML pages today, so those three show "needs server API" screens listing the endpoints required.  API_NOTES.md  has the full list:

• a token or JSON login (GitHub OAuth can't be used from the app),
• Books, Categories, Sites and Locations CRUD (CRUD = create, read, update, delete),
• Tickets plus comments,
• Files list and upload,
• JSON Songs CRUD.
